# Future lab authoring template

Use this scaffold for a new activity or a confirmed omission. Existing functioning
labs do not need identical headings. Preserve their URLs, outcomes, rubrics and
submission requirements. This template creates no additional student assignment.

## Title and scope

Current lab number/title; core or optional status; outcomes; planning time and its
basis. Add an independent activity ID only after a registry is deliberately adopted.
Record prerequisites, supported environment, required permissions and synthetic data.

## Enterprise scenario and concept

Explain the organizational problem and the architecture/governance boundary.
Identify what is supplied, what the learner builds and what remains conceptual.
Treat classification, governance and accountability across the lifecycle, rather
than implying they occur only after analytical processing.

## Before starting

Link required previous activities and the canonical setup route. State the working
directory, safe stopping point and how to resume. Do not repeat installation steps.

## Ordered activity

For each task, state its purpose, prediction where useful, command or edit,
expected observation and next action on failure. Distinguish an expected permission
denial from a faulty command. Automate setup friction while preserving independent
work required by the stated learning objectives.

## Independent investigation and interpretation

Ask learners to change or evaluate a bounded case, explain the result and identify
a tradeoff. A successful supplied runner does not complete the reasoning task.

## Validation and private evidence

State the observable success criterion and the existing assessment expectations.
Use demonstrated, simulated, proposed and untested evidence accurately. Specify
one private submission route; avoid duplicate essays/templates and public logs.
Provide textual equivalents for instructional images and equivalent evidence formats.

## Troubleshooting and recovery

Document likely failures, safe retries and scoped recovery. A destructive reset
requires an explicit reason, warning and disposable scope; prefer preserving work.
Test commands on the supported environment and record the exact revision/scope.
